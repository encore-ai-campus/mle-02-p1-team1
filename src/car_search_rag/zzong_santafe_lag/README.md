## 코드리뷰 준비·중복 코드 정리 — 2026-10-05

처리 흐름·파일별 역할·모델·저장 구조·실험 결과와 남은 검토 범위를 [코드리뷰 설명 안내](./code_review_guide.md)에 정리했습니다. 먼저 1~6절을 읽고 마지막의 1분 발표문으로 설명을 연습할 수 있습니다. [30번 결과 확인 노트북](../../../notebooks/30_code_review_overview.ipynb)은 공개 설정과 저장 요약만 읽으며 API·DB를 호출하지 않습니다.

- `source_profile.py`: 여러 파일에 반복되던 승인 원문 작업 ID·PDF/입력 식별값·개수를 한곳에 모았습니다. 값과 승인 범위는 유지하며 최신 작업을 자동 선택하지 않습니다.
- `search_support.py`: 로컬/OpenAI의 Supabase 프로젝트 확인과 저장 벡터 정렬 코드를 공유합니다. 기존 로컬 SQL 의미 검색 분기는 유지합니다.
- `retrieval.py`: 부모·자식·안내도의 TF-IDF 생성 설정을 공통 함수로 묶고 현재 검색 방식에 맞게 주석을 보완했습니다. 글자 단위·검색 가중치·표 값·정답 목록은 변경하지 않았습니다.

## 최신 확인 — 새 질문과 Precision@5 (2026-10-05)

## 팀 공유용: 현재 청킹·이미지 연결 방식

우리 방식은 **주제별 부모 기록 + 128토큰 이하 자식 청크 + 부모에 연결한 이미지 참조**입니다. 팀원이 제안한 소제목 묶음·텍스트 청크·이미지 ID 구조와 기본 방향이 비슷합니다. 현재 자동 주제는 목차 제목·인쇄 쪽수를 이용한 초안으로, 모든 소제목 경계와 계층 경로가 검토 완료된 것은 아닙니다.

| 팀원 공유 구조 | 현재 개인 프로젝트의 대응 항목 |
|---|---|
| 문서 document_id | documents와 processing_runs의 문서·모델·처리 작업 정보 |
| section_id / section_title / full_text | 부모 record_id / title / content, 보존 원문 raw_text |
| section_path | 현재 chapter_id·title로 일부 구분. 전체 계층 경로는 미완성 |
| 텍스트 chunk_id / chunk_order | 자식 record_id / chunk_index, parent_record_id로 원문 연결 |
| pdf_pages | source_pages. 자식에도 부모 범위를 보존하며 개별 문장의 정확한 페이지 판별 완료를 뜻하지 않음 |
| 관련 이미지 ID / 이미지 자료 | record_images로 부모와 images 연결, PDF 쪽수·내부 키로 파일명 중복 구분 |
| caption / image_path | 사람이 확인한 description과 local_path·Storage 경로. 설명·파일이 없는 참조도 있음 |

- **청킹:** 일반 글은 문장 경계를 우선하고 제목을 포함해 최대 128토큰입니다. 긴 문장은 한도에 맞춰 더 나누며, 확인한 안내도 번호 항목·표 행은 관계를 보존하도록 별도 처리합니다.
- **문맥:** 작은 청크로 검색한 뒤 전체 주제와 필수 각주·경고를 함께 읽습니다. 부모 527개·자식 2,213개입니다.
- **이미지:** 주제가 걸친 페이지의 그림을 우선 연결합니다. 같은 페이지에 있다는 이유만으로 해당 소제목의 정확한 그림이라고 확정하지 않습니다. 미검토 연결은 초안 상태로 유지합니다.
- **임베딩·저장:** 한국어 로컬 텍스트 모델 `jhgan/ko-sroberta-multitask-mrl`, 768차원, 개인 Supabase PostgreSQL/pgvector 스키마를 사용합니다. 그림 자체를 임베딩하지 않고 확인한 그림 설명을 검색 글에 포함합니다.
- **현재 범위:** 고유 그림 참조 864개, 부모–그림 연결 1,157개이며 설명이 있는 연결은 12개입니다. 실제 Storage 업로드 파일은 3개입니다. 숫자를 전체 이미지 이해·업로드 완료로 설명하지 않습니다.
- **팀 비교:** 차종·질문 난이도가 다른 각자 점수를 직접 비교하면 청킹 차이만의 효과를 알기 어렵습니다. 같은 PDF·고정 질문·복수의 유효 근거·같은 모델과 검색 설정으로 비교해야 합니다. 근거 찾기와 그림 대응·답변 정확도도 구분합니다.

## 노트북에서 Python 파일로 바뀌는 점

노트북은 셀을 하나씩 실행하면서 결과를 확인하는 실험 기록입니다. Python 파일은 확인한 작업을 함수로 묶어 같은 순서로 다시 실행하는 프로그램입니다.

예를 들어 노트북의 “PDF 읽기” 셀은 `pdf_reader.py`의 `inspect_pdf()` 함수가 되었습니다. 함수는 입력을 받아 정해진 일을 한 뒤 결과를 돌려주는 작은 작업 묶음입니다.

**처리 순서:** PDF 읽기 → 주제별 원문 묶기 → 확인한 표 보완 → 작은 청크 만들기 → 임베딩 → 근거 검색.

전체 원문 묶음을 **부모 기록**, 검색하기 좋은 작은 조각을 **자식 청크**라고 부릅니다. 작은 청크로 찾은 뒤 답변에 필요한 원문·각주·주의사항은 부모 기록에서 읽습니다.
