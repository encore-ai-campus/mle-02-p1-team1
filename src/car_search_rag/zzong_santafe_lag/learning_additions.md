# 수업 기반과 프로젝트 추가 적용 기록

기록일: 2026-10-01. 대상은 개인 Python 코드와 `notebooks/01~12`입니다.

[프로젝트 추가] 개인 코드를 `src/car_search_rag/zzong_santafe_lag/`로 이동했습니다. 프로젝트 루트 계산과 import·실행 경로를 수정했고, 노트북 13·14번의 코드 경로 및 관련 노트북의 문서 링크도 갱신했습니다. DB 스키마와 데이터 경로는 기존 이름을 유지합니다. 공통 로더가 개인 SQL을 읽지 않도록 `.sql.txt`로 보관하고 개인 세션에서만 등록합니다. 노트북의 저장된 출력과 셀 번호는 보존했으며 DB SQL을 실행하지 않았습니다.

## 주석을 읽는 방법

- **[수업 개념]**: 아래에서 확인한 수업 자료에 나온 방식입니다.
- **[프로젝트 적용]**: 배운 개념을 이 PDF와 실행 환경에 맞춰 사용한 설명입니다.
- **[프로젝트 추가]**: 싼타페 자료에 맞춰 직접 정한 규칙·구조·실험 설정입니다.
- **[모델 추가]**: 확인한 수업 자료에서 찾지 못했고 개인 실험에서 추가한 모델입니다.

`프로젝트 추가`는 그 개념을 수업에서 전혀 배우지 않았다는 뜻이 아닙니다. 수업 자료와 동일하지 않은 **이 프로젝트의 구체적인 처리**를 표시합니다. 수업 자료가 추가되면 근거를 다시 확인해 기록을 갱신합니다.

## 2. 프로젝트에서 추가한 모델

**현재 모델: `jhgan/ko-sroberta-multitask-mrl`**

- 확인한 자연어처리·LLM·RAG 수업 노트북에서는 이 모델을 찾지 못했습니다.
- [02번 모델 비교](../../../notebooks/02_embedding_model_comparison.ipynb)에서 수업에도 나온 MiniLM과 같은 PDF 샘플·질문으로 비교했습니다.
- 당시 10개 샘플·27개 질문에서 jhgan 후보는 첫 결과 24/27, 상위 3개 27/27이었습니다. MiniLM은 각각 23/27, 25/27이었습니다. 이 작은 차이로 우선 후보를 정했으며 일반적인 모델 우열을 확정한 결과는 아닙니다.
- 현재 설정은 768차원·128토큰 한도·로컬 CPU 실행입니다. 입력은 PDF 글과 확인한 그림 설명입니다.
- 선택 이유는 [config.py](./config.py), 실행 설명은 [embedding.py](./embedding.py), 입력 길이 설명은 [chunking.py](./chunking.py)에 주석으로 남겼습니다.
- 교체할 때는 모델 이름뿐 아니라 토크나이저·입력 한도·차원을 확인하고 청크를 다시 준비해야 합니다. 문서와 질문은 같은 모델로 임베딩합니다. 기존 문서 벡터를 그대로 두고 질문 모델만 바꾸면 검색 점수를 올바르게 비교할 수 없습니다.
- 향후 DB에 저장한 뒤 모델을 바꾸면 벡터 차원·모델 이름·버전·재임베딩 및 별도 저장 계획도 함께 정합니다.

## 4. 주석을 추가한 범위와 앞으로의 기록 방법

### DB 준비 단계 추가 (2026-10-01)

- `[프로젝트 적용]` 기존 SQL Mapper의 이름 있는 SQL과 파라미터 바인딩을 재사용합니다.
- `[프로젝트 추가]` PDF·처리 버전·부모·청크·그림·주제와 그림 연결을 개인 6개 테이블로 설계했습니다. 이유는 원문 보존, 처리 결과 혼합 방지, 반복 그림 이름 구분입니다.
- `[프로젝트 추가]` `database.py`의 개인 세션은 `mappers/`만 검색하고 `ZZONG_DB_URL`을 사용합니다. 공통 `MAPPER_ROOT`·팀 `DB_URL`은 바꾸지 않습니다.
- `[프로젝트 추가]` JSONB 변환과 pgvector 파라미터 전달, 모델·버전을 비교하는 의미 검색을 준비했습니다. 기존 결합 검색의 재현이나 전체 저장 완료를 뜻하지 않습니다.
- DBeaver에서 DB 연결과 vector 0.8.0/public을 확인하고, 사용자 승인 후 개인 스키마의 빈 테이블 6개를 생성했습니다. 읽기 전용 용량 조회로 합계 192KiB를 확인했습니다. Python 개인 연결·조회도 실행했으며 자료 저장·Storage 업로드는 하지 않았습니다.
- `[프로젝트 추가]` 전체 부모 527개·청크 2,213개의 글/JSON 바이트와 768차원 벡터 저장 공식을 이용해 저장량을 계산했습니다. 전체 DB 한 버전은 약 15~30MB로 추정하며 아직 실제 자료 저장량은 아닙니다. PDF는 별도 34.5MB이고 전체 그림 파일 크기는 미측정입니다. 계산 범위와 한계를 `db_guide.md`에 기록했습니다.

### 개인 연결과 표본 행 변환 추가 (2026-10-01)

- `[프로젝트 적용]` SQL Mapper의 SELECT로 개인 테이블의 건수·용량을 읽었습니다. Python과 DBeaver 연결은 따로 설정합니다.
- `[프로젝트 추가]` 팀 `.env`는 유지하고 개인 폴더 `.env`의 `ZZONG_DB_URL`을 사용합니다. 기존 설정을 읽기 전용으로 대조한 뒤 분리했고 Git 제외를 확인했습니다. 비밀번호와 주소는 결과에 출력하지 않습니다.
- `[프로젝트 추가]` Supabase 중계기가 시작 옵션을 반영하지 않아 `SET TRANSACTION READ ONLY`로 이번 연결의 트랜잭션만 읽기 전용으로 지정했습니다. `read_only=on`, 여섯 테이블 0행을 확인했습니다. 공통 파일·DB 기본 설정은 수정하지 않았습니다.
- `[프로젝트 추가]` `db_rows.py`는 기존 원문·청크·그림 딕셔너리를 별도의 DB 행으로 복사합니다. PDF SHA-256, 글 SHA-256, UUID 연결 번호와 원래 출처·검토 상태를 보존합니다. 새 모델과 라이브러리는 추가하지 않았습니다.
- `[프로젝트 추가]` 44·45쪽과 43쪽 표·각주를 포함한 부모 4개·청크 11개·이미지/연결 각각 3개의 메모리 미리보기를 실행했습니다. 43쪽 상호 필수 연결을 유지하고 방문 목록으로 순환을 막습니다. 새 필수 연결은 임의로 만들지 않습니다.
