# 싼타페 HEV 매뉴얼 챗봇 작업 계획

이 문서는 개인 프로젝트의 현재 합의 사항과 작업 순서를 한곳에 정리한다. 코드를 처음 배우는 사람도 각 파일의 역할을 알 수 있도록 쉬운 말로 설명한다.

## 1. 현재 합의한 프로젝트 범위

- **만들 것:** 싼타페 HEV 사용 설명서를 근거로 답하는 챗봇
- **자료:** 제공된 싼타페 HEV PDF 한 개
- **자료 범위:** 차량 관련 외부 데이터 API를 가져오지 않는다. 강사님이 PDF만으로 진행하는 방향을 확인했다.
- **답변 원칙:** 답변에 사용한 설명서 페이지를 표시한다. 설명서에서 근거를 찾지 못하면 내용을 추측하지 않고 “제공된 설명서에서 확인할 수 없습니다”라고 안내한다.
- **웹 검색:** PDF만으로 진행한다는 현재 범위에서는 챗봇 답변에 웹 검색을 섞지 않는다. 나중에 웹 검색을 추가하려면 프로젝트 범위와 출처 표시 방법을 먼저 다시 정한다.
- **저장 방식:** Supabase의 PostgreSQL 데이터베이스를 사용하고, 벡터 검색에는 pgvector를 쓴다. 데이터베이스 쿼리는 팀 예제의 SQL Mapper 방식으로 작성한다.
- **팀원 데이터 보호:** 다른 팀원의 테이블·파일·설정을 수정하거나 삭제하지 않는다. 내 전용 테이블과 Storage 경로를 새로 만들어 그 안에만 저장한다.
- **최종 목표:** PDF의 일반 글자뿐 아니라 그림·도표 안의 정보도 찾아 답할 수 있는 챗봇을 만든다.
- **작업 방식:** 팀원이 하나의 챗봇을 같이 구현하는 방식이 아니라, 각자 자기 브랜치에서 챗봇을 만든다.
- **내 작업 브랜치:** `zzong/santafe-lag`
- **PDF 파일:** `data/santafe_hev_manual.pdf`에 있는 원본 파일은 로컬 작업 자료로 사용한다. README의 공통 안내처럼 원본 데이터는 Git에 올리지 않는 것을 원칙으로 한다.

> 수업의 일반 M0 예시는 공개 API의 사용 가능 여부를 확인하지만, 이 프로젝트는 강사님 확인에 따라 싼타페 PDF만 자료로 사용한다. 따라서 API 확인 대신 PDF 파일 확인과 프로젝트 범위 확인을 M0 완료 기준으로 삼는다.

## 2. 챗봇이 답하는 방식

1. 사용자의 질문을 받는다.
2. 설명서에서 질문과 관련 있는 내용을 찾는다.
3. 찾은 내용을 바탕으로 짧게 답하고, 근거 페이지를 표시한다.
4. 관련 근거가 없으면 모른다고 말한다.

예를 들어 설명서에서 “타이어 공기압은 몇인가요?”의 근거를 찾으면 페이지와 함께 답한다. 반대로 설명서에 없는 최신 리콜 정보는 이 프로젝트의 자료만으로 확인할 수 없다고 안내한다.

## 3. 수업 노트북과 프로젝트 Python 파일의 차이

| 작업 | 주로 쓸 곳 | 쉬운 설명 |
| --- | --- | --- |
| PDF 몇 페이지를 읽어 보고 글자가 잘 뽑히는지 확인 | `notebooks/`의 `.ipynb` | 실험 기록장. 한 단계씩 실행하고 결과를 바로 본다. |
| 반복해서 쓸 개인 PDF 읽기·검색 기능 | `src/zzong_santafe_lag/`의 `.py` | 확인한 실험을 다시 실행할 수 있도록 정리한 프로그램 파일이다. |
| 데이터베이스에 넣고 꺼내는 문장 | 기능별 `.sql` | PostgreSQL에 실행할 SQL을 Python 코드와 분리해 둔다. |

노트북에서 먼저 작은 실험을 하고, 이해한 코드를 Python 파일로 옮겨 재사용한다. 노트북과 Python 파일은 서로 다른 방식으로 경쟁하는 것이 아니라, **실험은 노트북에서, 반복 실행할 기능은 Python 파일에** 두는 관계다.

새 기능은 저장소 SQL Mapper 규칙에 맞춰 `이름.py`, `이름_service.py`, `이름.sql`을 나란히 둔다.

- `이름.py`: 실행을 시작하고 입력을 받는 곳
- `이름_service.py`: PDF 읽기, 임베딩, 저장, 검색 순서를 연결하는 곳
- `이름.sql`: 데이터베이스에서 실행할 SQL 문장을 적는 곳

Supabase는 PostgreSQL을 제공하는 관리형 서비스이므로, DB 접속 주소를 연결해 기존 `psycopg`와 SQL Mapper 방식을 재사용하는 방향으로 진행한다. 다만 Supabase 접속 주소와 pgvector 확장이 실제 프로젝트에서 준비되어 있는지는 M4 저장을 시작하기 전에 확인한다. 현재 공통 SQL 로더는 `car_search/*.sql`만 읽으므로 개인 폴더 SQL의 등록 방법도 저장 단계에서 정한다.

공통 DB 연결과 SQL 실행 코드는 먼저 읽고 재사용한다. 커피 머신 예제의 공통 파일을 싼타페용으로 덮어쓰지 않는다.

**글자와 이미지는 같은 방식으로 청킹하지 않는다.** 글자는 문장·문단·페이지 단위로 나눈다. 이미지는 PDF에서 그림 영역을 따로 추출하고, 페이지 번호와 이미지 설명 또는 OCR 결과를 연결해야 검색에 사용할 수 있다. pgvector에는 이미지 파일 자체가 아니라 검색에 쓰는 벡터를 저장한다. 이미지 파일은 Supabase Storage에 두고 DB에는 파일 위치·페이지·설명·벡터를 저장하는 방식을 우선 검토한다. 이 저장 위치와 이미지 분석 방법은 PDF 구조를 확인한 뒤 확정한다.

### 팀원 데이터와 분리해서 저장하기

Supabase Storage는 파일을 폴더 경로로 정리할 수 있지만, PostgreSQL 데이터베이스에는 폴더 대신 **테이블**을 만든다. 그래서 파일과 DB 자료를 각각 내 전용 이름으로 분리한다.

- **이미지 파일:** 내 전용 Storage 버킷 또는 경로를 새로 만든다. 예: `zzong-santafe-hev/manual-images/`
- **DB 자료:** 내 전용 테이블을 새로 만든다. 예: `zzong_santafe_documents`, `zzong_santafe_chunks`, `zzong_santafe_images`
- **SQL Mapper:** 싼타페 전용 `.sql` 파일에 내 테이블만 대상으로 하는 쿼리를 작성한다.
- **보호 규칙:** 기존 팀원 테이블과 파일은 수정·삭제하지 않는다. `DROP`, 전체 테이블 `TRUNCATE`, 조건 없는 `DELETE`를 사용하지 않는다.
- **저장 전 확인:** 실행할 SQL의 대상 테이블과 Storage 경로를 확인하고, 작은 샘플을 내 전용 공간에 저장해 조회까지 확인한다.

위 이름은 충돌을 피하기 위한 예시다. 실제 저장을 시작하기 전 사용할 수 있는 이름인지 확인하고, 다른 팀원 자료와 분리되는지 확인한다.

## 4. 작업 순서

| 단계 | 할 일 | 완료됐다고 볼 기준 |
| --- | --- | --- |
| M0 범위 정리 | 주제, PDF 자료, 답변 원칙, 저장 기술을 확정 | 이 문서의 합의 내용과 강사님 확인이 기록됨 |
| M1 자료 확인 | PDF의 텍스트와 이미지가 페이지별로 어떻게 들어 있는지 살펴봄 | 페이지 번호, 텍스트, 그림·표 위치와 추출 상태를 확인하고 문제가 있는 페이지를 기록함 |
| M2 전처리·청킹 | 글자는 문맥을 유지하도록 나누고, 이미지·표는 별도 자료로 추출해 페이지 정보와 연결함 | 글자 청크와 이미지 자료의 전후 예시 및 선택 이유가 남음 |
| M3 탐색 | 목차·장·페이지별 길이와 문서 구성을 살펴봄 | PDF의 구조와 검색에 주의할 부분을 설명할 수 있음 |
| M4 벡터 저장 | 텍스트 청크와 이미지 설명의 검색 정보를 Supabase PostgreSQL + pgvector에 저장 | SQL Mapper로 저장한 자료·페이지·벡터를 다시 조회함. 이미지 파일 저장 위치도 확정함 |
| M5 답변 연결 | 검색 결과에서 글자와 이미지 정보를 활용해 설명서 근거 답변을 구성 | 페이지 근거를 포함하고 근거가 없을 땐 모른다고 답함 |
| M6 검색 평가 | 질문과 정답 페이지를 모은 평가 세트로 검색 품질을 측정 | Hit@5와 MRR을 계산하고 결과를 기록함 |
| M7 개선 실험 | 청크 크기·분할 방식 등 한 가지 조건을 바꾸어 비교 | 변경 전후 결과와 선택 이유가 표로 남음 |
| M8 화면 구성 | 사용자가 질문하고 답변·페이지 근거를 볼 화면을 만듦 | 기본 질문부터 출처 확인까지 직접 사용 가능함 |
| M9 시연·정리 | 시연 흐름과 한계, 다음 개선점을 정리 | 다른 사람이 프로젝트 목표와 결과를 이해할 수 있음 |

M6의 Hit@5 0.70 이상, MRR 0.50 이상은 초기 계획의 **목표값**이다. 아직 측정한 결과가 아니므로 달성했다고 쓰지 않는다.

## 5. 실험 기록 방법

검색 방식을 바꾸기 전에 기준 결과를 남긴다. 한 번에 한 가지 조건만 바꾸면 무엇 때문에 결과가 달라졌는지 이해하기 쉽다.

| 기록 항목 | 적을 내용 |
| --- | --- |
| 실험 이름 | 예: 페이지 단위 청크 기준 실험 |
| 질문 | 평가에 사용한 질문 목록 또는 버전 |
| 바꾼 조건 | 청크 크기, 분할 방식 등 이번에 바꾼 한 가지 |
| 결과 | Hit@5, MRR, 대표 검색 결과 |
| 배운 점 | 어떤 질문에서 좋아지거나 나빠졌는지 |

초기 비교는 페이지 단위 분할을 기준으로 시작하고, 이후 장·절 단위 분할을 비교한다. 평가 질문과 정답 페이지는 약 20~30개부터 준비한다.

## 6. 안전하게 작업하는 규칙

- 작업 브랜치는 `zzong/santafe-lag`를 사용하고 `main`에는 직접 수정하지 않는다.
- 실험 노트북은 `notebooks/`, 원본 PDF는 로컬 `data/`에 둔다.
- API 키와 DB 접속 주소는 `.env`에 두고 Git에 올리지 않는다.
- 코드의 새 함수와 중요한 처리에는 이해하기 쉬운 한국어 주석을 추가한다.
- DB 저장·삭제 SQL은 Python 문자열 안에 직접 쓰지 않고 해당 `.sql` 파일에 둔다.
- 등록 코드를 실행하기 전에는 기존 데이터가 삭제·교체되는지 서비스와 SQL을 먼저 확인한다.

## 7. 현재 진행 상태와 바로 다음에 할 일 (2026-10-01)

- PDF 779쪽과 이미지 참조 864개를 조사했다. 목차·색인과 본문을 구별해 주제를 묶었다.
- 안내도, 표, 글자·그림 예제를 확인했고, 패들 쉬프트 기호와 오일 표의 행·각주를 원본 화면과 대조했다.
- 노트북 11~12번에서 부모 원문 527개와 검색 청크 2,213개를 만들고 로컬 768차원 모델로 임베딩했다.
- 같은 30개 질문에서 목적별 검색은 첫 후보 26/30, 상위 3개 후보 28/30에 기존 기대 출처를 포함했다. 생성 답변의 정확도나 M6의 Hit@5·MRR 달성 수치가 아니다.
- 버클 질문은 PDF 110쪽에도 유효한 근거가 있다. 차단 클립 질문의 도난 경보 후보는 근거가 될 수 없어 추가 검색 개선이 필요하다.
- 전체 부모 중 507개는 자동 초안이다. 청킹과 전체 그림 검토가 완성됐다고 판단하지 않는다.
- 반복 실행할 코드를 `src/zzong_santafe_lag/`에 정리했다. `manual.py`는 실행, `manual_service.py`는 처리 순서다. 미리보기와 전체 임베딩·30문항 비교를 실행해 노트북의 개수 및 검색 결과와 일치함을 확인했다. 개인 폴더의 README에서 첫 실행 방법을 확인한다.

다음은 Python 미리보기 실행 결과를 이해하고, 검색 후보의 근거·그림 연결과 미검토 구간을 살펴보는 것이다. 사용자가 정한 순서대로 Python 정리를 마친 뒤 SQL/Supabase 저장 단계로 넘어간다. 현재 DB에 저장하거나 이미지·청크·벡터 데이터 파일을 새로 저장하지 않는다.
